<Note>This datasource is only available for Node.js agents.</Note>

The SQL datasource connects directly to SQL databases with automatic schema introspection. Each database table or view maps to a Forest collection - tables offer full read-write capabilities while views are read-only.

## Basic usage

```javascript
import { createAgent } from '@forestadmin/agent';
import { createSqlDataSource } from '@forestadmin/datasource-sql';

const agent = createAgent(options);

agent.addDataSource(
  createSqlDataSource({
    uri: 'postgresql://user:pass@localhost:5432/mydb',
    sslMode: 'preferred'
  })
);
```

## Automatic schema introspection

By default, the SQL datasource automatically discovers your database structure when the back-end starts. It extracts:

- **Tables and views** - Each becomes a collection
- **Columns** - With automatic type detection
- **Primary keys** - For record identification
- **Foreign keys** - Converted to relationships
- **Indexes** - Used for query optimization

This requires database credentials with access to `information_schema`. Ownership roles are recommended.

<Info>
Introspection is supported for PostgreSQL, MySQL, MariaDB, and Microsoft SQL Server.
</Info>

### What it costs at boot

Introspection reads the **whole schema**, every time the back-end starts:

- Every table and view in the schema is listed and described, whatever `include` and `exclude` say. Those options publish or hide collections *after* the datasource is built, so they do not shrink the scan — exposing one collection out of four hundred still reads four hundred tables.
- Column, index and foreign-key metadata is fetched per table, concurrently and without a ceiling, so a wide schema issues hundreds of catalog queries at once.
- Model and relation building then runs on the event loop of whatever process hosts the agent.

On a small schema this is invisible. On a large one it is a burst of concurrent catalog queries against your production database, repeated on every boot, restart and redeploy — enough to show up as a performance hit while the database is also serving traffic.

If that describes your database, two things help:

- [**Pre-compute the introspection**](#pre-compute-the-introspection) to take the scan off the boot path. It works whatever your [deployment topology](/get-started/connect/architectures/deployment-options), and it is worth doing once the boot is long enough to notice — on a modest schema the default is fine and the extra file is not worth maintaining. The trade is that the file becomes a snapshot you have to regenerate on every migration; automate it alongside them rather than relying on anyone to remember.
- **Time the scans that still hit production.** A first boot of a new back-end, or a deploy that has not adopted the file, scans a database that is also serving your users — put those outside your busy hours. This applies to live scans only, not to generating the file.

## Configuration options

### Connection URI

The connection URI format varies by database:

<CodeGroup>
```javascript
createSqlDataSource({
  uri: 'postgresql://user:password@host:5432/database'
})
```

```javascript
createSqlDataSource({
  uri: 'mysql://user:password@host:3306/database'
})
```

```javascript
createSqlDataSource({
  uri: 'mssql://user:password@host:1433/database'
})
```
</CodeGroup>

### SSL configuration

Control SSL/TLS connection behavior:

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  sslMode: 'preferred' // or 'verify', 'required', 'disabled', 'manual'
})
```

**SSL modes:**
- `preferred` - Use SSL if available, otherwise unencrypted (default)
- `required` - Require SSL, fail if unavailable
- `verify` - Require SSL with certificate verification
- `disabled` - Never use SSL
- `manual` - Custom SSL configuration (advanced)

### Schema selection

Specify which database schema to use (PostgreSQL, SQL Server):

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  schema: 'my_schema' // default: 'public'
})
```

### Connection pooling

Configure connection pool for optimal performance:

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  pool: {
    max: 20,        // Maximum connections
    min: 5,         // Minimum connections
    acquire: 30000, // Max time (ms) to get connection
    idle: 10000     // Close idle connections after 10s
  }
})
```

### Read replicas

Distribute read operations across replica databases:

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  replication: {
    write: { host: 'primary.example.com' },
    read: [
      { host: 'replica1.example.com' },
      { host: 'replica2.example.com' }
    ]
  }
})
```

### SSH tunnel

Connect through an SSH tunnel:

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@localhost:5432/db',
  ssh: {
    host: 'ssh-host.example.com',
    port: 22,
    username: 'ssh-user',
    privateKey: require('fs').readFileSync('/path/to/private-key')
  }
})
```

### SOCKS5 proxy

Route connections through a SOCKS5 proxy:

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  proxySocks: {
    host: 'proxy.example.com',
    port: 1080,
    username: 'proxy-user',
    password: 'proxy-pass'
  }
})
```

### Connection timeout

Set maximum time to establish connection:

```javascript
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  connectionTimeoutInMs: 5000 // 5 seconds
})
```

## Soft-deleted records

Display records marked as deleted (soft deletes):

```javascript
// Show soft-deleted for specific collections
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  displaySoftDeleted: ['users', 'projects']
})

// Show soft-deleted for all collections
createSqlDataSource({
  uri: 'postgresql://user:pass@host:5432/db',
  displaySoftDeleted: true
})
```

This is useful when your application uses soft deletes (e.g., `deleted_at` column) and you want to manage deleted records in Forest.

## Pre-compute the introspection

The introspection is JSON-serializable. Produce it once with the exported `introspect()` helper, commit the file, and hand it back to `createSqlDataSource` as its second argument. The datasource then skips the catalog scan entirely and builds its models from the file.

**Worth adopting when the boot cost is real** — a wide schema, frequent deploys, a database under load, or a back-end sharing a process with your application. On a small schema the default introspection is fine, and a committed file is one more thing to keep current. Skipping the scan has been supported since the first release of `@forestadmin/datasource-sql`: the format is versioned, older files are migrated forward automatically, and Forest's own CLI builds its typings from an introspection rather than a live connection.

<Steps>
  <Step title="Generate the file">
    Run this once, and again on **every** migration. Wire it into the step that runs your migrations, or a release script, so the file cannot fall behind the database — the agent never re-checks it against the live schema, so a file that is out of date is simply believed.

    Nothing here needs a time window. The scan runs once per migration, against the database your pipeline just migrated, and replaces one that would otherwise run on every boot of every instance — so it belongs in continuous integration like any other build step. The exception is a pipeline that generates the file against production itself: treat that run as a live scan and keep it out of your busy hours.

    ```javascript
    // scripts/introspect.mjs
    import { introspect } from '@forestadmin/datasource-sql';
    import { writeFileSync } from 'fs';

    const introspection = await introspect(process.env.DATABASE_URL);

    writeFileSync('./introspection.json', JSON.stringify(introspection, null, 2));
    ```
  </Step>
  <Step title="Boot from it">
    ```javascript
    import { createSqlDataSource } from '@forestadmin/datasource-sql';
    import { readFileSync } from 'fs';

    const introspection = JSON.parse(readFileSync('./introspection.json', 'utf8'));

    agent.addDataSource(
      createSqlDataSource(process.env.DATABASE_URL, { introspection })
    );
    ```
  </Step>
</Steps>

**What it buys you:**
- No catalog scan at boot, so restarts and redeploys stop hammering `information_schema`
- A schema change shows up as a reviewable diff in your pull request
- Runtime credentials no longer need `information_schema` access
- The back-end boots against a database that is momentarily slow or unreachable for metadata

<Warning>
**The file is a snapshot, and nothing checks it for you.** When an introspection is supplied, the datasource builds its models from it and never compares it against the live database — so after a migration, a new column stays invisible and a dropped one is still advertised, until you regenerate. There is no warning: a stale file is simply believed.

A [`.forestadmin-schema.json`](/reference/schema/forestadmin-schema) drift check does not cover this. That check regenerates the Forest schema from the same introspection file, so a stale file produces a stale schema that matches what is committed, and the build stays green. Regenerating the introspection on every migration is what keeps both honest.

Only the format is handled automatically: older introspection versions are migrated forward on load.
</Warning>

<Note>
`introspection` is an option on `createSqlDataSource`'s **second** argument. The `schema` key on the first argument is unrelated — it selects the Postgres schema to read (`public` by default).
</Note>

## Live Query support

Enable SQL-based reporting by setting a connection identifier:

```javascript
createSqlDataSource({
  uri: process.env.DATABASE_URL,
  liveQueryConnections: 'main_database'
})
```

This allows authorized users to create Live Query charts and segments that execute custom SQL directly against your database.

<Warning>
Live Queries execute raw SQL. Ensure proper access controls and review queries before deploying to production.
</Warning>
