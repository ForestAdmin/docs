[Architecture](/get-started/connect/architectures/self-hosted) describes the two ways to run the Forest back-end — in-app and standalone. This page is for choosing between them: which one your situation calls for, and what each commits you to afterwards.

The decision is one question. Does the Forest back-end run as its own service, or inside an application process you already have?

**Default to standalone.** Not because it is faster — it does exactly the same work — but because it keeps the back-end's lifecycle out of the process serving your users. Go in-app when something on this page actually requires it.

## What genuinely requires in-app

<Steps>
  <Step title="You are on Ruby">
    Standalone deployment is currently available for Node.js only. On Ruby, Forest ships a Rails integration, so the back-end the Forest UI talks to runs inside your application. If you need standalone deployment with Ruby, please [contact our sales team](https://www.forestadmin.com/contact).

    That does not mean everything has to live in one process. Ruby can distribute the data work across [RPC back-ends](/get-started/connect/data-sources/rpc) — separate services that a main back-end aggregates — which is how you keep a heavy datasource off the process serving your users.
  </Step>
  <Step title="Forest needs your application's live runtime">
    Not your code — your *running* code. An in-process service you cannot reach over HTTP, a transaction the agent must join, an in-memory cache or singleton your business logic depends on. Sharing a process is the only way to share those.

    If what you actually need is to call your business logic, an internal endpoint the agent calls gets you there without merging the processes.
  </Step>
</Steps>

## What does not require it

<AccordionGroup>
  <Accordion title="Reusing your ORM models">
    Model reuse does not need a shared process. `createSequelizeDataSource` takes any Sequelize instance, so what it needs is your model definitions to be **importable** — a shared codebase, not a shared runtime. If yours already sit in a monorepo, [you can have the reuse and a separate process at once](#if-your-code-already-lives-in-a-monorepo).

    The reuse is worth having. Scopes, associations and validations come across, and with [`datasource-sql`](/get-started/connect/data-sources/sql) you rebuild them by hand. It is simply not an argument for in-app.

    Whether it is available to you at all depends on your ORM. Forest reads your data through a [datasource](/get-started/connect/overview), the connector between the back-end and a database, an API or an ORM. Four of them read an ORM's model definitions: Sequelize and Mongoose on Node.js, ActiveRecord and Mongoid on Ruby. Every other stack — TypeORM, Prisma, Drizzle, Knex, raw SQL — connects through [`datasource-sql`](/get-started/connect/data-sources/sql), which reads the database itself and builds its own model layer. There is then nothing to reuse either way, and the question drops out of the decision entirely.
  </Accordion>
  <Accordion title="Introspection and boot cost">
    Standalone does not boot faster. It introspects exactly as much as in-app, and [pre-computing the introspection](/get-started/connect/data-sources/sql#pre-compute-the-introspection) removes that work from both.

    What standalone moves is the CPU and event-loop cost: the scan, the model building and the schema generation happen in a process your users are not waiting on.

    The database load is shared either way. Those catalog queries hit the same database your application queries, so a heavy introspection can still lengthen your application's own requests from a separate process. [Pre-computing the introspection](/get-started/connect/data-sources/sql#pre-compute-the-introspection) is what removes that half, for both topologies.
  </Accordion>
  <Accordion title="Sharing a database connection">
    Two processes against one database is normal. It costs you a second connection pool, which is a number to set deliberately, not an obstacle.
  </Accordion>
</AccordionGroup>

| | Standalone | In-app |
| --- | --- | --- |
| Restarts when you deploy the application | No | Yes |
| Competes for your application's event loop | No | Yes |
| Can take the application down by crashing | No | Yes |
| Deploys and scales independently | Yes | No |
| Can reuse your ORM models | Yes, from a shared codebase | Yes |
| Can use your application's live runtime | No | Yes |
| Available for Ruby | Not for the main back-end — see [RPC back-ends](/get-started/connect/data-sources/rpc) | Yes |

## What in-app actually shares

Sharing a process shares four things, and only the first is obvious:

- **Memory and connection budget.** Two connection pools against one database, each with its own ceiling. Set [`pool`](/get-started/connect/data-sources/sql#connection-pooling) deliberately rather than taking the default on both sides.
- **The restart schedule.** Every deploy of your application restarts the agent, and every deploy of the agent restarts your application.
- **The event loop.** Agent startup — [schema introspection](/get-started/connect/data-sources/sql#what-it-costs-at-boot), model building, schema generation — runs on the loop your application serves requests from. On a wide schema that is a stall, not a delay: your application's own requests queue behind it, and it happens on every deploy and every restart, not once at install.
- **The crash surface.** An error thrown out of agent construction that nothing catches exits the process, taking your application with it.

None of this is hypothetical on a large schema, and none of it is visible on a small one.

You can measure most of it before production: boot against an anonymised copy of the real database and you get the true schema width, so the scan takes the time it will take. What a copy will not reproduce is the contention — an event-loop stall only costs you something while your application is serving real traffic on that loop, so staging shows you the duration without the consequence.

Which is the argument for caution on the first boot specifically. **Bring a new back-end up outside core hours**, on either topology, and keep any deploy that still introspects live out of your busy window.

<Warning>
The boot also puts real load on the database, and that part is true of both topologies — see [what introspection costs at boot](/get-started/connect/data-sources/sql#what-it-costs-at-boot). In-app is what adds your application's own request latency on top of it. If the schema is wide enough for either to bite, [pre-computing the introspection](/get-started/connect/data-sources/sql#pre-compute-the-introspection) takes both off the boot path.
</Warning>

## If your code already lives in a monorepo

Living in the same repository and running in the same process are different decisions, and the first does not force the second. If your application is already a monorepo, this is how you reuse its models without giving up a separate process — not a reason to restructure a repository that is laid out some other way.

Add the agent as its own workspace package with its own `package.json`, import the models from the package that defines them, and start it with `mountOnStandaloneServer()`:

```typescript
// packages/forest-agent/src/index.ts
import { createAgent } from '@forestadmin/agent';
import { createSequelizeDataSource } from '@forestadmin/datasource-sequelize';

// The same model definitions your application uses — imported, not shared at runtime.
import sequelize from '@acme/models';

createAgent({
  authSecret: process.env.FOREST_AUTH_SECRET,
  envSecret: process.env.FOREST_ENV_SECRET,
  isProduction: process.env.NODE_ENV === 'production',
})
  .addDataSource(createSequelizeDataSource(sequelize))
  .mountOnStandaloneServer(Number(process.env.PORT))
  .start();
```

Your scopes, associations and validations come across, and no introspection runs at boot because the models are already declared. The agent opens its own connection pool from those definitions, in its own process.

You keep shared tooling, shared CI and shared types. You do not keep the shared process. Deploy that package as its own service.

<Note>
On TypeORM, Prisma, Drizzle or any stack Forest reads through the database rather than your models, swap the import for [`createSqlDataSource`](/get-started/connect/data-sources/sql) with a pre-computed introspection. The rest of the shape is identical — the workspace package and the standalone mount are what matter here.
</Note>

If the agent genuinely needs your application's service layer — and not merely its models — that is a case for an internal API the agent calls, not for merging the two processes.

## Running two agents at once

During a [migration](/guides/migration/from-v1/overview) you may want the current agent and the new one live at the same time. Separate processes are recommended — you are running both so that one stays steady while the other is restarted, and a shared process gives up that separation — and if they share a host, give them separate paths.

The paths are the part that is not negotiable. An agent mounted at a prefix answers **every** request under it. Two agents on one host at the same prefix do not coexist — one of them takes all the traffic, and the symptom is either the wrong agent answering with the wrong environment secret, or an environment that appears dead for no visible reason.

Give the second agent its own hostname, or set [`prefix`](/reference/agent-api/nodejs) and change that environment's URL in Forest to match:

```typescript
createAgent({ ...options, prefix: '/forest-v2' })
```

<Warning>
The two changes must land together. Setting `prefix` without updating the environment URL in Forest leaves the new agent unreachable; updating the URL without setting `prefix` gives a 404. Either half looks exactly like a broken deployment.
</Warning>
