---
title: "Migrating from Agent v1 to v2"
description: "Complete guide to moving your setup from a legacy agent to the current generation."
---

This guide covers migrating from any v1 agent (`forest-express-sequelize`, `forest-express-mongoose`, `forest-rails`, `django-forestadmin` v1) to the current generation.

The migration unlocks workflows, the MCP server for AI agents, multi-datasource, decision traces, and everything Forest has shipped since the original admin-panel era. Most teams complete the migration in 1-2 days with zero downtime.

## What v2 changes

The new generation is a rebuilt agent with a cleaner, more composable customization API. The biggest changes you'll see during migration:

- **Multi-datasource is native.** A single agent can connect to multiple databases and APIs.
- **Customization happens via a fluent API on collections.** `agent.customizeCollection('users', users => users.addField(...))`.
- **Computed fields declare their dependencies explicitly.** `dependencies: ['firstName', 'lastName']`.
- **Relationships are first-class.** Many-to-one, one-to-many, many-to-many, and external relations replace most legacy "smart relationships".
- **Routes are no longer overridden directly.** Most v1 route overrides become hooks or computed fields.

## Before you start

<Steps>
  <Step title="Upgrade the agent you are migrating away from">
    Do this first, before any v2 work. A migration means repeated restarts of the legacy agent, and old releases handle a cold restart badly: `@forestadmin/forestadmin-client` before **1.36.2** caches failed permission lookups for the full 15-minute TTL, so one slow response during a restart locks users out of that environment until the cache expires. Bring the legacy agent up to date and you turn a possible outage into a blip.
  </Step>
  <Step title="Decide where the new agent will run">
    Settle this before you write any code — it is the decision that is expensive to reverse, and the one most often taken by default. See [Deployment options](/get-started/connect/architectures/deployment-options).

    During the migration specifically, run the two agents in **separate processes**, and if they share a host give them distinct prefixes or hostnames.
  </Step>
  <Step title="Migrate into a new environment, not a new project">
    Everything you have built in the UI — layouts, segments, dashboards, workspaces, roles, teams, scopes — belongs to the **project**, and nothing carries across project boundaries. A new project starts empty and has to be rebuilt by hand.

    Add an environment to the project you already have (**Project Settings → Environments → Add**), point it at the new agent, and your configuration is still there.
  </Step>
  <Step title="Inventory your customizations">
    List every Smart Action, Smart Field, Smart Relationship, Smart Segment, and route override in your current project. Each step page below covers one of these surfaces.
  </Step>
  <Step title="Back up your project">
    Export your current Forest project layout. While the layout is preserved across the agent swap, having a baseline is good practice.
  </Step>
  <Step title="Plan parallel running">
    Both agents can run side by side during migration, in separate processes.
  </Step>
</Steps>

<Warning>
**Running both agents in one process is not recommended.** It works, but the two then share a restart schedule, an event loop and a crash surface: every deploy restarts the legacy agent as well, while the new one is still being redeployed. The fallback you are relying on becomes as unsettled as the thing you are testing. Separate processes avoid that, and separate hosts more so.

Routing is the one hard constraint. Two agents answering the **same path on the same host** do not coexist, whatever process they run in: one of them takes all the traffic. Give the new agent its own hostname, or its own `prefix` with the environment URL in Forest changed to match.
</Warning>

## Migration steps

<Steps>
  <Step title="Install the new agent">
    Install the new packages alongside your existing ones. The legacy agent keeps running in its own process; the new one runs in a separate process on a different port, so restarting one never restarts the other.

    <Tabs>
      <Tab title="Node.js">
        ```bash
        npm install @forestadmin/agent
        npm install @forestadmin/datasource-sql
        # or @forestadmin/datasource-mongo, @forestadmin/datasource-mongoose, etc.
        ```
      </Tab>
      <Tab title="Ruby">
        ```bash
        # Gemfile
        gem 'forest_admin_agent'
        gem 'forest_admin_rails'
        gem 'forest_admin_datasource_toolkit'
        gem 'forest_admin_datasource_customizer'
        gem 'forest_admin_datasource_active_record'
        ```
      </Tab>
    </Tabs>
  </Step>
  <Step title="Migrate datasources">
    Re-declare your data sources using the new datasource API. See [Datasources](/guides/migration/from-v1/steps/datasources).
  </Step>
  <Step title="Match the old names exactly — this is a gate">
    Your layout addresses every column, filter and action by **name**. If the new agent exposes `first_name` where the old one exposed `firstName`, nothing errors: the field is simply treated as new, and everything configured against the old name silently detaches. On a mature project that is hundreds of broken views discovered one at a time.

    Whether anything moved depends on what each side reads. `forest-rails` published your column names and `forest-express-sequelize` published your Sequelize attribute names; on the new side, the ORM datasources keep your attribute names while `datasource-sql` publishes the column. Close this before migrating any customization — see [Datasources](/guides/migration/from-v1/steps/datasources#match-the-names-your-layout-already-uses) for the mapping, and for how to prove the match offline against your existing `.forestadmin-schema.json`.
  </Step>
  <Step title="Migrate Smart Actions">
    Convert each Smart Action to the new `addAction` API. See [Smart Actions](/guides/migration/from-v1/steps/smart-actions).
  </Step>
  <Step title="Migrate Smart Fields">
    Convert computed fields to `addField` with explicit dependencies. See [Smart Fields](/guides/migration/from-v1/steps/smart-fields).
  </Step>
  <Step title="Migrate Smart Relationships">
    Convert legacy smart relationships to native relations or external relations. See [Smart Relationships](/guides/migration/from-v1/steps/smart-relationships).
  </Step>
  <Step title="Migrate Smart Segments">
    Update segments to use condition trees instead of ORM-specific queries. See [Smart Segments](/guides/migration/from-v1/steps/smart-segments).
  </Step>
  <Step title="Rehearse against your real layout">
    A branch starts from production's layout, so you can render all of it against the new agent without touching production:

    ```bash
    forest branch migration-rehearsal --origin production
    ```

    Anything you got wrong in the naming gate shows up here as a dead column or a broken action. This is cheaper than populating a shared environment, and it is usually enough.
  </Step>
  <Step title="Populate a shared test environment (optional)">
    Only if your team needs a shared pre-production to click through. A fresh environment starts with a **default** layout, not a copy of production's, so transport it explicitly:

    ```bash
    forest layout:pull --env production --team Operations --with-workflows
    forest layout:apply forest-layout.json --env node-test --team Operations --with-workflows --force
    forest roles:copy --from production --to node-test
    ```

    `layout:pull` and `layout:apply` resolve **one team at a time**, so run that pair once per team — a shell loop over your team names with `--force` does it unattended. `roles:copy` is environment-level and runs once. Keep the colons: with a space, the command prints help and exits successfully without transporting anything. See the [CLI reference](/reference/cli/overview).
  </Step>
  <Step title="Test side by side">
    Run both agents simultaneously, in separate processes. Point the test environment at the new agent and verify behavior matches the legacy one, especially actions, computed fields, and segments.
  </Step>
  <Step title="Switch your environment URL">
    Once you're confident, update your production environment's URL to point at the new agent. That is the whole cutover: same project, same environment, same `FOREST_ENV_SECRET`, and your layout, roles, workspaces and workflows are untouched.
  </Step>
  <Step title="Keep the rollback available">
    Rolling back is the same change reversed — point the environment URL back at the legacy agent, which takes seconds and leaves the layout alone. Keep the legacy agent deployed and running until you no longer want that option.
  </Step>
  <Step title="Remove legacy packages">
    Once production has been stable on the new agent for a few days, remove the legacy packages and clean up the old code.
  </Step>
</Steps>

## What's preserved

Your Forest UI configuration is **not** affected by the agent migration:

- Layouts, segments, dashboards, charts
- Roles, permissions, scopes, teams
- Workspaces, workflows, inboxes
- Approval workflow configurations
- Smart Action visibility settings

These all live in Forest's UI configuration and continue to work as long as the new agent exposes the same collection and field names.

<Warning>
All of it is scoped to the **project**, not to the agent. Swapping the agent under an existing environment preserves everything above; standing up a second project preserves none of it, and there is no supported way to copy it across. Migrate into a new environment of the project you already have.
</Warning>

## Common issues

<AccordionGroup>
  <Accordion title="Field names changed between v1 and v2">
    Names are case-sensitive, and a Sequelize model mapping a `camelCase` attribute onto a `snake_case` column was published under the attribute name by `forest-express-sequelize`. `datasource-sequelize` still is, so that pairing holds; `datasource-sql` publishes the column instead. Restore the old names with the `rename` option on `addDataSource` (collections) and `renameField` (fields) rather than editing the layout — see [Datasources](/guides/migration/from-v1/steps/datasources#match-the-names-your-layout-already-uses).
  </Accordion>
  <Accordion title="My ORM has no datasource (TypeORM, Prisma, Drizzle...)">
    Sequelize, Mongoose, ActiveRecord and Mongoid have a matching datasource, and so do Django and SQLAlchemy on the Python agent. On Node.js, other ORMs — TypeORM, Prisma on SQL, Drizzle, Knex — connect through [`datasource-sql`](/get-started/connect/data-sources/sql), and Prisma on MongoDB through [`datasource-mongo`](/get-started/connect/data-sources/mongodb). Both read the database itself and build their own model layer, so they cannot read your entities. That works, and it is the normal path, but two consequences follow: your application's model callbacks never fire on a write from Forest, and unless you pre-compute it, the agent pays a full-schema introspection at every boot. Both are covered in [deployment options](/get-started/connect/architectures/deployment-options).
  </Accordion>
  <Accordion title="A model callback stopped firing">
    Whether a callback fires depends on how the datasource writes:

    - **`datasource-sequelize`** writes through bulk methods, so per-record hooks such as `beforeCreate` do not run. See [which hooks run](/get-started/connect/data-sources/sequelize#which-hooks-run-on-a-write-from-forest).
    - **`datasource-mongoose`** writes through `insertMany`, `updateOne` and `updateMany`, which skip `save` middleware.
    - **The ActiveRecord datasource** writes one record at a time, so `after_save` and the rest fire as they always have. Nothing to migrate.
    - **The Mongoid datasource** fires them on create and on a single-record edit, but not on a multi-record edit or a delete.
    - **`datasource-sql`** never loads your models, so no callback of yours runs at all.

    For a callback that does not fire, triage by one question: **must this fire when an operator edits the record in Forest?** If yes, reimplement it as an [agent hook](/product/process/advanced-concepts/hooks/overview), or have the hook call an internal endpoint in your application. Do not reimplement one that still fires, or it runs twice.
  </Accordion>
  <Accordion title="Can I reuse my v1 .forestadmin-schema.json?">
    No — never copy it into the new agent. The file is generated output describing what the agent exposes, and the two generations do not write the same shape. Let the new agent generate its own, then use the old one as a **reference** to diff against while you close the naming gate.
  </Accordion>
  <Accordion title="A Smart Action's form behaves differently">
    The Smart Action form API is more structured in v2. Fields are declared explicitly. See [Smart Actions](/guides/migration/from-v1/steps/smart-actions) for the new form syntax.
  </Accordion>
  <Accordion title="A computed field is slow">
    The new agent supports batched computed fields: `getValues` receives an array of records. If you naively port a v1 `get` function inside a `.map(async ...)`, you'll keep the same N+1 problem. Aggregate the underlying query.
  </Accordion>
  <Accordion title="A relationship doesn't appear in the UI">
    The new relationship API requires you to declare both sides. If you only declared one direction, the UI may not surface it. See [Smart Relationships](/guides/migration/from-v1/steps/smart-relationships).
  </Accordion>
</AccordionGroup>
