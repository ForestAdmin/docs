---
title: "Migrating datasources"
description: "Move your datasource configuration from a legacy agent to the current generation."
---

In legacy agents, the datasource was tied to a single ORM (Sequelize, Mongoose, ActiveRecord, Mongoid). The new agent introduces an explicit datasource layer that supports multiple databases and APIs in the same agent, and decouples the connection from the framework.

## API cheatsheet

| Legacy agent | New agent |
| --- | --- |
| `forest-express-sequelize` | `@forestadmin/agent` + `@forestadmin/datasource-sql` |
| `forest-express-sequelize` (with Sequelize models) | `@forestadmin/agent` + `@forestadmin/datasource-sequelize` |
| `forest-express-mongoose` | `@forestadmin/agent` + `@forestadmin/datasource-mongoose` |
| `forest-rails` (ActiveRecord) | `forest_admin_agent` + `forest_admin_rails` + `forest_admin_datasource_active_record` (+ toolkit, customizer) |
| `forest-rails` (Mongoid) | `forest_admin_agent` + `forest_admin_rails` + `forest_admin_datasource_mongoid` (+ toolkit, customizer) |

<Note>
  Pick `datasource-sql` or `datasource-mongo` if you want Forest to introspect the database directly. Pick `datasource-sequelize`, `datasource-mongoose`, or `datasource-active-record` if you want to reuse your existing ORM models (recommended when your application already defines them).
</Note>

## Before (Node.js, forest-express-sequelize)

```javascript
const Liana = require('forest-express-sequelize');
const models = require('./models');

app.use(Liana.init({
  modelsDir: __dirname + '/models',
  envSecret: process.env.FOREST_ENV_SECRET,
  authSecret: process.env.FOREST_AUTH_SECRET,
  sequelize: models.sequelize,
}));
```

## After (Node.js, reusing Sequelize models)

```javascript
import { createAgent } from '@forestadmin/agent';
import { createSequelizeDataSource } from '@forestadmin/datasource-sequelize';
import { sequelize } from './models';

const agent = createAgent({
  authSecret: process.env.FOREST_AUTH_SECRET,
  envSecret: process.env.FOREST_ENV_SECRET,
  isProduction: process.env.NODE_ENV === 'production',
});

agent.addDataSource(createSequelizeDataSource(sequelize));

agent.mountOnExpress(app).start();
```

## After (Node.js, direct SQL connection)

If you don't want to reuse your ORM models, connect directly to the database. Forest introspects the schema automatically.

```javascript
import { createAgent } from '@forestadmin/agent';
import { createSqlDataSource } from '@forestadmin/datasource-sql';

const agent = createAgent({
  authSecret: process.env.FOREST_AUTH_SECRET,
  envSecret: process.env.FOREST_ENV_SECRET,
  isProduction: process.env.NODE_ENV === 'production',
});

agent.addDataSource(
  createSqlDataSource({
    uri: process.env.DATABASE_URL,
    sslMode: 'preferred',
  })
);

agent.mountOnExpress(app).start();
```

## Before (Ruby, forest-rails with ActiveRecord)

```ruby
# Gemfile
gem 'forest_liana'

# config/initializers/forest_liana.rb
ForestLiana.env_secret = ENV['FOREST_ENV_SECRET']
ForestLiana.auth_secret = ENV['FOREST_AUTH_SECRET']
```

## After (Ruby, ActiveRecord)

```ruby
# Gemfile
gem 'forest_admin_agent'
gem 'forest_admin_rails'
gem 'forest_admin_datasource_toolkit'
gem 'forest_admin_datasource_customizer'
gem 'forest_admin_datasource_active_record'
```

Run `rails generate forest_admin_rails:install` to scaffold the two configuration files.

```ruby
# config/initializers/forest_admin_rails.rb
ForestAdminRails.configure do |config|
  config.auth_secret = ENV.fetch('FOREST_AUTH_SECRET')
  config.env_secret = ENV.fetch('FOREST_ENV_SECRET')
end
```

```ruby
# app/lib/forest_admin_rails/create_agent.rb
module ForestAdminRails
  class CreateAgent
    def self.setup!
      database_configuration = Rails.configuration.database_configuration
      datasource = ForestAdminDatasourceActiveRecord::Datasource.new(database_configuration[Rails.env])

      @create_agent = ForestAdminAgent::Builder::AgentFactory.instance.add_datasource(datasource)
      customize
      @create_agent.build
    end

    def self.customize
      # Collection customizations (Smart Actions, computed fields, segments) go here.
    end
  end
end
```

## Multi-datasource

The biggest payoff of migrating: the new agent can connect to multiple data sources at once.

```javascript
const agent = createAgent({ /* ... */ });

// Primary database (Sequelize models reused)
agent.addDataSource(createSequelizeDataSource(sequelize));

// Analytics database (direct SQL)
agent.addDataSource(
  createSqlDataSource(process.env.ANALYTICS_DATABASE_URL),
  { name: 'analytics' }
);

// Stripe data
agent.addDataSource(
  createStripeDataSource({ secretKey: process.env.STRIPE_SECRET_KEY })
);
```

Cross-datasource relationships are first-class. See [Relationships](/product/process/relationships/overview).

## Configuration changes

| Concept | Legacy | New |
| --- | --- | --- |
| `envSecret` | `FOREST_ENV_SECRET` | `FOREST_ENV_SECRET` (unchanged) |
| `authSecret` | `FOREST_AUTH_SECRET` | `FOREST_AUTH_SECRET` (unchanged) |
| Models directory | `modelsDir` option | Provided implicitly via the datasource (Sequelize / ActiveRecord) |
| Including / excluding tables | Manual model filtering | `{ include: [...], exclude: [...] }` on `addDataSource` |
| Schema generation | Forest CLI / runtime | `.forestadmin-schema.json` written on agent start in development |
| Custom routes | Express routes | Hooks (see [Hooks](/product/process/advanced-concepts/hooks/overview)) |

## Including or excluding collections

In v1, you'd manually filter the models passed in. In v2:

```javascript
agent.addDataSource(
  createSequelizeDataSource(sequelize),
  { exclude: ['internal_logs', 'session_data'] }
);

// Or only include specific collections
agent.addDataSource(
  createSequelizeDataSource(sequelize),
  { include: ['users', 'orders', 'products'] }
);
```

<Note>
These options decide what Forest **publishes**. They are applied to a datasource that has already been built, so with [`datasource-sql`](/get-started/connect/data-sources/sql#what-it-costs-at-boot) the full schema is still introspected at boot whatever you list here. To cut that cost, [pre-compute the introspection](/get-started/connect/data-sources/sql#pre-compute-the-introspection).
</Note>

## Match the names your layout already uses

Your existing layout — every column, filter, sort, segment and action configured over the years — addresses collections and fields by **name**. The agent swap preserves all of it on one condition: the new agent exposes the same names as the old one.

A mismatch does not raise an error. The field simply reads as new, and everything configured against the old name detaches silently.

Whether you have any renaming to do depends on what each side reads, not on your language. Both v1 agents published a name, and each v2 datasource publishes one:

| Reads | Publishes |
| --- | --- |
| `forest-rails` | the database column name |
| `forest-express-sequelize` | the Sequelize **attribute** name, which parts company with the column as soon as a model uses `underscored` or an explicit `field` mapping |
| `datasource-sequelize`, `datasource-mongoose`, `datasource-active-record` | the model's attribute keys, the same names your ORM already uses |
| `datasource-sql`, `datasource-mongo` | the database column or field name, from introspection |

So a Sequelize project keeping its models through `datasource-sequelize` usually has nothing to rename: a `firstName` attribute over a `first_name` column was published as `firstName` before and still is. The same project moving to `datasource-sql` gets `first_name` and does. Where the two sides disagree, restore the old names explicitly:

```javascript
// Collections: a function, or an explicit map
agent.addDataSource(createSqlDataSource(process.env.DATABASE_URL), {
  rename: { user_accounts: 'userAccounts' },
});

// Fields: on the collection customizer
agent.customizeCollection('userAccounts', collection =>
  collection.renameField('first_name', 'firstName'),
);
```

### Prove the match before you deploy

You do not need a running environment to check this. The new agent can build its schema from an introspection file with no database connection, which lets you diff it against the schema your legacy agent already produces:

<Steps>
  <Step title="Capture the introspection once">
    ```javascript
    import { introspect } from '@forestadmin/datasource-sql';
    import { writeFileSync } from 'fs';

    writeFileSync(
      './introspection.json',
      JSON.stringify(await introspect(process.env.DATABASE_URL)),
    );
    ```
  </Step>
  <Step title="Generate the new schema without a database">
    `buildDisconnectedSequelizeInstance` turns that file into models with no connection at all, so the loop is fast enough to run on every change:

    ```javascript
    import { createAgent } from '@forestadmin/agent';
    import { buildDisconnectedSequelizeInstance } from '@forestadmin/datasource-sql';
    import { createSequelizeDataSource } from '@forestadmin/datasource-sequelize';
    import { readFileSync } from 'fs';

    const introspection = JSON.parse(readFileSync('./introspection.json', 'utf8'));
    const sequelize = await buildDisconnectedSequelizeInstance(introspection, () => {});

    // The same mapping your real agent uses.
    const rename = { user_accounts: 'userAccounts' };

    await createAgent({
      authSecret: process.env.FOREST_AUTH_SECRET,
      envSecret: process.env.FOREST_ENV_SECRET,
      isProduction: false,
      // A file of its own, so the legacy agent's .forestadmin-schema.json survives for the diff.
      schemaPath: './.forestadmin-schema.v2.json',
    })
      .addDataSource(createSequelizeDataSource(sequelize), { rename })
      .generateSchemaOnly();
    ```

    Apply the same `rename` and customizations here that your real agent uses, or the diff tells you nothing.

    <Warning>
    Keep `schemaPath` pointing at a file of its own. Its default is `.forestadmin-schema.json`, the path the legacy agent writes, so leaving it unset overwrites the file you are about to diff against and the check passes no matter what.
    </Warning>
  </Step>
  <Step title="Diff against the legacy schema">
    Compare the collection and field names in `.forestadmin-schema.v2.json` with those in the legacy agent's `.forestadmin-schema.json`. Add `rename` and `renameField` entries until the name sets match.
  </Step>
</Steps>

An empty diff is a mechanical guarantee that your layout will still bind. Treat it as the gate for the rest of the migration.

<Warning>
Use the legacy `.forestadmin-schema.json` as a reference only. Never copy it into the new agent — it is generated output, and the two generations do not write the same shape.
</Warning>

## Validate the migration

After swapping the datasource:

<Steps>
  <Step title="Start the new agent">
    Run on a different port from the legacy agent (e.g. `3001`).
  </Step>
  <Step title="Check schema generation">
    On first start in development, the agent writes a `.forestadmin-schema.json` file. Confirm every collection you expect is listed.
  </Step>
  <Step title="Smoke-test the API">
    Hit `http://localhost:3001/forest`, which should return Forest metadata.
  </Step>
  <Step title="Point a test environment at the new agent">
    Update the agent URL in your Forest test environment. Browse collections. Every collection should appear with the same fields.
  </Step>
  <Step title="Continue with customizations">
    Once data flows correctly, move on to migrating Smart Actions, Smart Fields, and the rest.
  </Step>
</Steps>

## Common issues

<AccordionGroup>
  <Accordion title="A column shows up with a different name">
    Some legacy agents auto-converted snake_case to camelCase. The new agent preserves database column names by default. Use the `rename` option or the field-rename customization API to align names.
  </Accordion>
  <Accordion title="A relationship I had isn't appearing automatically">
    Foreign keys defined in the database are detected automatically. Relationships defined only in your ORM models (`belongsTo`, `hasMany`) are detected when you use the ORM-backed datasources (`datasource-sequelize`, `datasource-mongoose`, `datasource-active-record`). Relationships that exist only in code paths the agent doesn't see won't be detected. Declare them explicitly with `addManyToOneRelation`, `addOneToManyRelation`, etc.
  </Accordion>
  <Accordion title="The agent fails to connect to the database">
    Verify that `DATABASE_URL` is set on the agent server, that the user has read permissions, and that SSL is configured if your database requires it. For SQL datasources, check `sslMode`.
  </Accordion>
</AccordionGroup>
